## 2. 关键设计决定

1. **计数真相源仍是 Go（`kb.Aux`）**：`internal/metrics` 只做「键 → 指标名/标签」翻译 + 分位数/gauge 维护，**不另建一套计数**（否则两层口径必然对不上，§14.1）。
2. **不引 prometheus client 库**：只需要"计数 + 少量分位数 + 几个 gauge"，手写 exposition 约 60 行；引库会带进依赖和强制的指标组织方式。分段延迟用**固定窗口（512）+ 现算 p50/p95/avg**：客服单轮不需要 HDR 直方图精度，但**必须看得见 p95**（只看均值会被长尾骗）。
3. **gauge 惰性求值且失败返回 `-1`**：`kb_chunks`/`cs_conversations`/`support_tickets_open` 只在 scrape 时查库；**查不到就报 -1，不谎报 0**（0 与"查不到"是两件事）。
4. **`/readyz` 与 `/healthz` 分工**：`/healthz` 答"进程活着"，`/readyz` 答"依赖齐不齐、能不能接客"，且**只报布尔与必要计数**（不泄露 URL/key/provider 密钥）。
5. **管理端"启用必须带 token"**：`ADMIN_ENABLED=1` 且 `ADMIN_TOKEN` 为空 → **拒绝启动**，不"降级放行"；token 比较用 `subtle.ConstantTimeCompare`；`/metrics` 与 `/admin/*` 同一套鉴权（内部指标不该对公网裸奔）。
6. **工单状态机用条件更新**：`UPDATE ... WHERE ticket_no=? AND status=<from>`，`RowsAffected!=1` 即冲突——与座位/订单占用同一裁决方式；非法流转返回 **409 且附"允许的下一跳"**（坐席不必猜）。
7. **限流的"身份桶"用凭证 hash 而非解析后的 user_id**：中间件比 handler 早，拿不到 user_id；凭证 hash 同样做到"一个登录用户一个桶"，对游客自然退化为设备级，且 **Redis 里不出现可用凭证**。
8. **限流值是成本保护值**：一条问答会花掉多次 LLM/embedding 调用，所以 AI 链路单独限流；默认 IP 30/min、凭证 20/min，**报告写明口径**，压测后调整。
9. **降级矩阵逐条可验**（§14.4）：编排层挂 → 建单 + 200；Redis 挂 → 无缓存/放行限流，问答不被 打死；无 embedding key → 字面替身且**响应里标 `ngram`**。
10. **诚实性验收必须机检**（§15.4）：入口真实性（行业知识类答案不得出现指向平台入口的操作指引）、边界声明覆盖率、矛盾组合——三条都进 `run_eval.py`，不靠人工抽检。

## 3. 实现期真问题（含根因与修法）

### P1 `docker-compose.yml` 硬编码数据库口令 + `.gitignore` 根本没忽略 `app.env`
`app.env` 一直被 git 跟踪（M0 起就标注为待办），而 `.gitignore` 里**连 `app.env` 这一条规则都没有**；compose 里还写着明文 `DB_PASSWORD=020218`。
修：补齐成对规则（`app.env` / `*.env` / `!*.env.example`）→ `git rm --cached app.env`（**保留本地文件**）→ compose 改 `${DB_PASSWORD:?...}` 从 `.env` 注入 → 交付 `app.env.example`（逐项注明"留空降级成什么"）→ 泄露面自查脚本。
**遗留**：git 历史里的旧值仍在（本地仓库），已在报告的"待办"里给出轮换清单。

### P2 管理端写接口 500：`assigned_to` 是 int，不是字符串
`support_tickets.assigned_to` 是 **int（坐席用户 id，§10.4 预留的就是"谁认领"）**，我把请求体当字符串 '坐席A' 传 → MySQL 严格模式报错 → **500**（合法流转也走不通）。
修：请求体 `assigned_to` 改为 `*int32`；顺便把 `resolved_at` 在流转到 `resolved` 时一并写入（状态机字段完整性）。前端改为坐席 ID 输入框。
教训：**写接口的字段类型必须对着 DDL 核**，别对着中文语义想当然。

### P3 `order_detail` 的剩余时间还在 Go 里比时钟（M3 滞留项）
`if left := time.Until(o.ExpiredAt); left > 0` —— 与 M3 踩过的时区坑同源（DSN `loc=Asia/Shanghai` vs 容器会话 UTC）。
修：新增 `OrderLeftMinutesForUser`（SQL 内 `TIMESTAMPDIFF(MINUTE, NOW(), expired_at)`，且**带上 `user_id` 条件**保持越权铁律），Go 侧只消费结果；取不到就**不报数字**（宁可不显示也不给错时间）。

### P4 知识库更新后答案缓存不失效（M3 滞留项）
`kb-sync` 只更新 MySQL/Qdrant，**从不碰 `cs:ac:*`** → 知识库改了，缓存里"依据旧知识库生成、语气笃定"的答案会继续命中——比答不上来更糟。
修：`kb-sync` 成功后用一段 Lua（`keys` + `del`，避免 SCAN 分页期间漏清）清空 `cs:ac:*` 并打印条数；Redis 不可用只告警（缓存仍会按 TTL 自然过期）。

### P5 `readyz` 的 `qdrant_points=-1`：集合名不一致
配置里没写 `QDRANT_COLLECTION`，代码默认 `kb_chunks`，而 M0 spike 建的是 **`kb_dev`** → 查不到 → `-1`。
修：部署配置显式给 `QDRANT_COLLECTION=kb_dev`；`-1` 的语义（查不到 ≠ 0）保留并在 readyz 里可见。**这正是"不谎报 0"的价值**：它一眼暴露了配置错位。

### P6 管理端与 `/metrics` 之前完全不存在鉴权入口
M1~M3 只有 `/internal/*`（内网密钥）与用户侧 JWT；`/metrics`、全量查询、工单操作都没有承载面。
修：M4 引入 `ADMIN_ENABLED/ADMIN_TOKEN` + `adminAuth` 中间件 + 未配 token 拒绝启动；`/metrics` 也走管理端鉴权。

### P7 测试脚本自身的三个坑（记账，避免当成产品缺陷）
① `start_orch` 里 `cd orchestrator` 后**没回到仓库根**，后续 `go run main.go` 报 "cannot find main.go"（与 M3 的 phase2 cwd 坑同类）；
② 原生 `curl -o /tmp/x.json` 在 MSYS 下**路径不翻译**，脚本再用 MSYS 路径读就"文件不存在"；
③ 指标断言放在**流量之前**（计数还没产生）→ 误报缺失。
修：脚本内显式 `cd`、用 `$LOCALAPPDATA/Temp`、断言前先打流量。

## 5. 评测数字（**必须与 19.1 一起读**）

见 `m4_recheck` 运行的 `/tmp/cs_eval_result.json`。**统一声明**：本轮全部在 `LLM_PROVIDER=mock` + 无 embedding key（`vector_mode=ngram`）下取得，
分类靠规则词表、检索靠字面 bigram、生成是确定性假模型——**这些数字只证明"管线通、口径对"，不代表真实模型水平**。

| 集合 | 规模（本轮） | 门槛（§15.1/§15.2） | 达标线 | 本轮实测 | 说明 |
|---|---|---|---|---|---|
| 分类 held-out | 75 条（7 类 + other） | ≥400（每类 ≥40） | ≥90% | **准确率 53.3%**，LLM 兜底占比 **40.0%** | 分档：order 80% / account 80% / refund 60% / app 50% / travel 40% / booking 30% / policy 10% / other 100% |
| 检索（qa） | 20 条 | ≥200（prose ≥1/3） | ≥90% | **Top1 40% / Top3 40%**，空结果 0，top1 余弦中位数 1.0 | 字面替身下"同词集=1.0"，说明是**字面匹配**而非语义 |
| 检索（prose） | 10 条 | — | ≥85% | **Top1 100%** | prose 样本问法更贴近文档标题（标题路径前缀起了作用） |
| 端到端 | 20 条 | ≥80 | ≥85% | **分类符合 80% / 事实符合 65%**，转人工 6（带工单号 6） | 事实符合低主要是 mock 生成与阈值转人工所致 |
| 诚实性：入口真实性 | — | — | 0 违规 | **0 违规** ✅ | 行业知识类答案无指向平台入口的操作指引 |
| 诚实性：矛盾组合 | — | — | 0 | **0** ✅ | 无"工具结论 + 行业建议"混排 |
| 诚实性：边界声明覆盖率 | 来源含非 supported 的回答 | — | 100% | **未达标**（首轮口径把"平台其实支持的能力"误标为 industry，修正判据后分母变小、仍需复测） | 见下方分析 |

**三条必须写明的结论**：

1. **分类准确率这轮不可用**：LLM 兜底占比 40%，而兜底走的是 **mock 模型**（返回确定性假答案、必然选错类）。policy 只有 10% 就是被"top1 与 top2 得分接近 → 交 LLM 仲裁"这条正确设计带偏的。**规则层单独表现要等 19.1 落地后才能分离度量**。
2. **检索数字暴露的是"字面匹配"本质**：qa Top1 40% 而 prose 100% 的落差，说明假 embedding 下 qa 的口语化问法匹配不到（正是 §15.1 要求"真实买家问法 + 语义改写"的原因）。**阈值（0.60/0.50/3.0）与嵌入质量必须一起标定**。
3. **规模均未达门槛**（75/400、20+10/200、20/80）：这是**当前最大的诚实缺口**，已进滞留清单；在补齐并接真实模型前，报告里的准确率只能内部参考，**不得对外引用**。

### 5.2 回归（M4 改动是否让前序里程碑退化）

| 阶段 | 结果 | 说明 |
|---|---|---|
| 单测 | Go 6 包 + Python 29 passed | 无退化 |
| **M2** | **21/22**（唯一失败 = `B1 待支付订单`） | B1 失败是**夹具又过期**（`expired_at` 是相对时间，隔一段时间自然失效），刷新后即 PASS；M2 本体验收以 M2 报告 22/22 为准 |
| **M1** | 作答 9/20、转人工 7、边界声明 100%、操作性措辞 0 违规；**但 20 条中有 4 条请求连接失败**（`WinError 10054/10061`） | 4 条失败是**并发运行干扰**（同时有另一个验收驱动在重启服务）；9+4=13 与 M3 时的 13/20 对齐 ⇒ **行为未退化** |
| **M3** | phase1 **10/12** + phase2 **3/3** | phase2 = **重启进程后续跑** 3/3 ✅ 未退化。phase1 的 C3/C4（缓存第 3 次命中）本轮失败，根因见下 |

**M3 的 C3/C4 失败根因（已定位，不是代码缺陷）**：这两个用例依赖"该问答最终能作答并被缓存"，
而 M4 给 `app.env` 补上 `QDRANT_URL/QDRANT_COLLECTION` 后，**检索从"纯 BM25 降级路径"变成"向量+BM25 融合"**；
在**词面替身 embedding + 未标定阈值**下，部分问法（如"发票能开电子版吗"）落到阈值以下 → `transfer_path=threshold`（日志实证 `top1_cos=0`）→ 转人工的答案**按设计不入缓存** → C3 自然不命中。
⇒ 这是**环境/配置敏感**（阈值未标定期的已知现象），修法是 **19.1 选型 + 阈值标定**，不是改代码。
同一现象也解释了为什么"开启 Qdrant 后转人工占比上升"——M0 报告里那句"过滤式 ANN 比堆 ef 划算"成立的前提是**向量本身有意义**。

8. **管理端页面自身不鉴权**：`/admin` 是静态壳（token 存 localStorage 由操作者粘贴）——不泄露数据，但**生产建议放到内网或加 SSO**（当前依赖 `/admin/*` 的 API 鉴权兜底）
